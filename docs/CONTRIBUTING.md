## 二、代码组织：按部门归属，禁止混放

改动落点必须与职责对应。**跨部门改动是本项目最常见的事故来源。**

```
server/src/
  agent/        收敛循环 · 上下文装配 · 历史治理 · 记忆 · 规划
  tools/        工具实现与契约
  mcp/          MCP 集成 · 工具注册表 · spill 归档
  model/        LLM 客户端与模型目录
  routes/       HTTP 接口
  db/           连接池 · 仓储
  config/       配置与运行时设置
  sse/          事件流
  scheduler/    定时触发
  path/         路径与数据根
client/src/
  features/     按功能切分（chat / sessions / settings / mcp / memory ...）
  services/     与后端契约的单一入口
  shared/       跨功能复用
```

**动手前先回答三个问题**：

1. 这个改动归哪个部门？
2. 现有部门能否承载？不能则说明是**架构缺口**，先补部门再改行为。
3. 这是架构问题还是实现 bug？

答不上来就先别写代码。

## 三、提交规范

提交信息用中文，格式为 `<类型>(<部门>): <做了什么>`：

```
fix(agent): A 方案落地 —— 图片只活一次请求，历史不再携带 base64
feat(memory): 换项目识别链二期 —— 项目名录 + 锚行拆分
docs(prompts): 收录 spill 事前规则的工具提示词
chore(script): 收录本轮诊断脚本
```

要求：

- 首行写清**行为差异**，不复述文件名。
- 正文写**依据**（实测数据 / 复现路径 / 契约出处），不写「优化了一下」。
- 一次提交只做一件事；架构调整与行为调整不同提交。

## 四、提交前必须通过

```bash
# 后端
cd server
cargo check --all-targets     # 必须零警告
cargo test                    # 必须全绿

# 前端
cd client
npm run typecheck             # tsc --noEmit
npm run build
```

**改了话术（`server/prompts/**/*.md`）也必须重编译** —— 话术经 `include_str!` 编译期嵌入，只改 `.md` 不重编译等于没改。

---

## 五、六条铁律

1. **改话术不改逻辑，改逻辑不改话术。** 行为调优去 `.md`，执行链路去 `.rs`。两边一起动 = 架构事故。
2. **每条契约只住一个文件。** 同一条纪律出现 N 处 = 模型读 N 遍，既费 token 又互相稀释。
3. **能被上游推导出来的不单独写一条**；同一个东西只给一个名字。
4. **边界只写在 schema 关键字里 = 没写。** 给模型看的只有 `description`，声明的 `minimum`/`maximum` 必须同时在描述里说清。
5. **防呆要响，不要静默降级。** 取不到内容就返回空 + `warn!`，别回落到「返回全文」——静默降级会把配置错误伪装成正常行为。
6. **加回/裁掉工具必须同步契约测试**（`mcp/registry_tests.rs` 的工具名单断言是工具面的对外契约，不是注释）。

---

## 六、前缀缓存三律（改上下文装配时必读）

工具面与话术都在**每次请求的最前段**，按未命中价付费。因此：

1. **静态模板在前，动态值在后。**
2. **条款顺序一旦稳定永不重排** —— 重排等于全量缓存失效。
3. **同场景措辞零变体**：禁时间戳 / 随机数 / 计数进入模板正文，计数只进尾部注入的对账块。

## 七、Pull Request

> 改动涉及架构、对外契约，或者你拿不准归属时，先 [开 Issue](https://github.com/Azzrenz/Real/issues)
> 说一句 —— 免得做完才发现方向不对。

1. Fork → 从 `main` 切分支，分支名 `feat/xxx`、`fix/xxx`。
2. 一个 PR 只解决一件事。附上复现步骤或实测数据。
3. 说明改动**落在哪个部门**、为什么不是别的部门。
4. 若改动涉及对外契约（工具面、HTTP 接口、配置项），在描述里明确列出。

评审关注点按优先级：**架构归属 → 契约一致性 → 行为正确性 → 代码风格**。

---

## 八、不要提交的东西

`.env`、任何真实 API Key、`real.db`、`target/`、`node_modules/`、`dist/`、日志与一次性诊断产物。

`.gitignore` 已覆盖绝大多数情况；提交前请跑一次 `git status --porcelain` 自查。
