# 结论与承诺的纪律

**每一句写进代码注释 / 缺口清单 / 文档的「X 是这样」，都要能指到一个 `read` 过的文件 + 行号。指不到，就写成「待验」。**

这不是严谨癖。一句没核对的判断，会让**下一步的量级判断**错掉。

## 真实代价

`crates/clef-app/src/ui/surface.rs` 的 `KNOWN_GAPS` 里写着：

> `automation.mode` —— 「自动化泳道存在但模式切换无控件；需建 LaneHandle 枚举」

下一轮抽查发现：`shell.rs` 里出现 33 次 automation，但**「泳道」全部指轨道行**（`arrange.rs:97 pub lanes: Vec<Rect>`）。自动化泳道**从未被画过**。

后果不是「少写了一个文件」——是缺口分类错了：

| 当时的判断 | 实际 | 量级差 |
|---|---|---|
| 缺控件 → 建个枚举 + 画矩形 | 缺绘制 → 写布局 + 曲线 + 命中 + 接线 | 一个数量级 |

## 「缺什么」必须先定性再动手

同一句「这里还缺东西」，至少有两种情况：

| 情况 | 判据 | 做法 |
|---|---|---|
| **缺控件** | 底层数据结构、求值函数、测试都在 | 建枚举 + 画矩形 + 接命中 |
| **缺功能** | 底层只有类型声明，没有实现 | 先写功能，枚举无从谈起 |

**判法：去底层找证据（数据结构 / 求值函数 / 测试名），不要看注释怎么写。** 注释是上一个人（很可能是你自己）写的假设。

## 承诺的下一步要兑现，或明说没改

上一轮结尾写「下一轮先抽查 3 条缺口定性」，下一轮直接动手没做，也没说明。用户看到的是一份**缺了一段**的进度报告。

- 做到了 → 在收尾里指出来（「抽查做了，结论推翻了上一轮」）。
- 没做到 → 写清「这轮改了计划，因为 X」。
- 计划本身要改 → 改，别假装还在原计划上。

## 一个不装的结论：规则挡不住这类错

上面两条能挡住的只是**有确定性信号**的错：`modify` 回执的 `old` 不对、编译报未覆盖变体。这两类会被立刻发现。

「未验证的判断写成事实」**没有信号**——「我没查」本身不产生任何可观察事件。所以它会再犯。

真正拦得住它的是**测试，不是规则**。这个项目里已经拦过好几次：

| 断言 | 拦住什么 |
|---|---|
| `executable_count_is_pinned` | 有人偷偷把 Unbound 改成假实现 |
| `gap_count_is_pinned` | 加了命令没画控件 |
| `every_hotkey_is_gated_by_the_typing_guard` | 热键不过 `typing` 闸门 |
| `the_compatibility_table_is_exactly_this` | 目标×动作兼容表漏格 |

规则改行为，测试改结果。**能写成断言的，不要只写成规矩。**
